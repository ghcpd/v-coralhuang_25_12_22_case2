## Root causes & fixes (concise) 💡
1. Full-table materialization (list users)
   - Root: code loaded all rows into memory then sliced in Python → huge CPU & IO under concurrency.
   - Fix: use SQL LIMIT/OFFSET to push pagination to DB; keep a single COUNT() when total is needed.
   - Benefit: avoids scanning and transferring entire table; reduces latency by orders of magnitude.

2. N+1 queries (user followers)
   - Root: fetched follower IDs then fetched each follower row in a separate query.
   - Fix: single JOIN to fetch follower rows with LIMIT/OFFSET.
   - Benefit: reduces query count and removes per-row round trips.

3. Indexes
   - Added indexes on `followers.followee_id` and `followers.follower_id` (present in schema) so COUNT/LIMIT queries are efficient.

Why minimal: the changes keep the same JSON contract (items, page, per_page, total), same auth behavior, and stable ordering — only the internal DB access patterns were improved.
