You are a senior backend engineer experienced in API performance tuning and database optimization.
You will work hands-on: modify real code, run real tests, and produce concrete before/after evidence.
Avoid speculative claims; support conclusions with measurements.

Sub-Type: Performance optimization

Scenario:
A paginated REST API implementation is too slow under concurrent access.

Single source of truth:
A canonical JSON file named `input` defines the workload, dataset assumptions, SLA thresholds,
required artifacts, and failure conditions.

Important execution note:
Due to local execution constraints (e.g. Windows environment),
performance validation does NOT require starting an external HTTP server or Gunicorn.
Instead, you must execute the workload by invoking the API handler logic directly
within the process, using concurrent execution to simulate load.

This approach is intentional and acceptable for this task, as long as:
- the same code paths used by the HTTP API are exercised,
- authentication logic is applied consistently,
- database access patterns and ORM behavior are preserved.

Do NOT ask the user to start a server, provide a token, or confirm service availability.
All required configuration is provided by `input`.

Your job:
Optimize the actual API implementation so that, when executing the workload defined in `input`,
measured latency improves meaningfully and ideally meets the SLA.
Preserve correctness and API semantics (authentication behavior, pagination logic,
stable JSON contract).

Execution steps:
1) Read `input`.
2) Seed the dataset if required.
3) Identify the core API handler functions corresponding to the endpoints in `input`.
4) Execute the baseline workload by invoking these handlers directly with concurrent execution.
5) Collect required artifacts (latency distribution, query counts, slow queries).
6) Identify performance bottlenecks (e.g. N+1 queries, redundant counts, missing indexes).
7) Apply minimal, well-justified optimizations.
8) Re-run the workload using the same in-process execution model.
9) Produce before/after artifacts and a concise optimization summary.

Deliverables:
- README.md explaining what was optimized, why, and how results were obtained.
- requirements.txt.
- run_tests: a one-command runner that:
  a) reads `input`,
  b) seeds data if needed,
  c) runs baseline and optimized workloads in-process,
  d) computes p50/p95/p99 latency and error rate,
  e) writes all required artifacts.
- Minimal patch set (code changes and/or DB migrations) needed to reproduce the improvement.
